# External comparison data for the paper

Evidence gathered 4 Aug 2026 to contextualise SecureAssist's OWASP Benchmark
false-positive rate. Curated by hand — not regenerated by the harness.

---

## 1. The claim this evidence supports

A high false-positive rate on OWASP Benchmark is the **normal outcome for any
tool that actually detects taint-flow vulnerabilities**, not a defect specific
to SecureAssist. Tools with low FP rates on this benchmark achieve it by
detecting almost nothing.

---

## 2. Modern evaluation (2026) — the strongest citation

**Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False
Positive Filtering**, arXiv:2601.22952, January 2026.
<https://arxiv.org/html/2601.22952>

Ran CodeQL, Semgrep, SonarQube and Joern on **OWASP Benchmark v1.2 — the same
2,740-case Java benchmark used here**.

| Tool | Non-vulnerable cases flagged positive | Notes |
|---|---|---|
| SonarQube | **94.6%** | 1,254 false positives (45.8% of benchmark) |
| Semgrep | **74.8%** | |
| CodeQL | **68.2%** | best F1 (74.4%), precision 60.3%, 904 FPs |
| Joern | low | but recall only **8.2%** — misses nearly everything |

Also reports that **LLM-based post-filtering reduced false-positive rates from
over 92% to 6.3%** — directly relevant as a future-work direction (see §6).

**Why this matters:** CodeQL is GitHub's flagship analyser, built over a decade
with whole-program analysis. Its 68.2% FP rate on this benchmark is
indistinguishable from SecureAssist's hybrid configuration.

### Read these figures carefully before citing them

**They are benchmark-wide (all 2,740 cases, all 11 categories).** SecureAssist's
figures cover only the five categories it targets. The mixes differ, so these
are not a like-for-like comparison — present them as *context on benchmark
difficulty*, never as a head-to-head table.

**Per-category behaviour diverges sharply from the aggregate.** SonarQube flags
94.6% of non-vulnerable cases benchmark-wide, yet its SQL-injection false-positive
rate is reported elsewhere as 1–10%. Both can be true: it detects almost no SQL
injection, and a tool that never fires in a category cannot produce false
positives there. Compare the same categories or say nothing.

**Do not confuse FPR with FDR.** OWASP's FPR is `FP/(FP+TN)` — the share of safe
cases flagged. False discovery rate is `FP/(FP+TP)` — the share of findings that
are wrong. Vendor material frequently quotes FDR. The two are not comparable, and
a tool can look excellent on one and terrible on the other.

**Prefer independent sources.** Vendor forums and marketing pages reporting a
tool's own benchmark performance are not evidence.

### Per-category figures — the one genuine like-for-like comparison

The paper publishes per-CWE accuracy and FPR heatmaps. Two rows are directly
comparable to SecureAssist because they are the same CWE on the same benchmark:

| CWE | CodeQL | Semgrep | SecureAssist |
|---|---|---|---|
| **CWE-327** (weak crypto) | **FPR 1.00** | **FPR 1.00** | **TPR 100%, FPR 0%** |
| CWE-330 (weak randomness) | FPR 1.00 | FPR 1.00 | not covered |
| CWE-89 (SQL injection) | 0.83 accuracy | — | see results table |
| CWE-78 (command injection) | 0.80 accuracy | — | see results table |

On CWE-327 both CodeQL and Semgrep flag **every** non-vulnerable case.
SecureAssist flags none and detects all true positives. This is a defensible
head-to-head claim: same CWE, same benchmark version, independent 2026 source.

The paper's own summary — *"residual FPs are concentrated in policy- and
cryptography-related CWEs, while injection-style vulnerabilities are filtered
reliably"* — is the mirror image of SecureAssist's profile, which is clean on
cryptography and noisy on injection. Worth discussing rather than hiding: the
two designs fail in opposite directions.

## 3. Methodology warning before quoting any Youden figure

The 54.7 reported elsewhere in this project is an **average of per-category
Youden scores**. The harness in `bench/score.js` reports both per-category rows
and an overall row **pooled across all cases**. These are different statistics
and will not agree.

Pick one, state which, and use it consistently. Mixing them in a single table
is the kind of inconsistency an examiner will find.

## 4. Why the false positives occur

From `fpAnalysis.js` over the held-out run — every OWASP "safe" case that
SecureAssist flagged, classified by the mechanism that makes it safe.
**Zero unclassified.**

| Mechanism | Share |
|---|---|
| Reflection | ~70% |
| Collection key indirection | ~14% |
| Switch on a folded constant | ~11% |
| Always-taken arithmetic branch | ~4% |
| Encoding round-trip | ~1% |
| **Realistic safe code** | **0%** |

Regenerate exact counts with `node bench/fpAnalysis.js`.

### The reflection case, worth printing in full

`ThingFactory.createThing()` reads a class name from `thing.properties` **at
runtime**, then instantiates it via `Class.forName(...)`. Which implementation
of `doSomething()` executes is not determinable from source.

On top of that, the taint chain is a **decoy**. `BenchmarkTest00332` propagates
the tainted value through StringBuilder, HashMap, substring, Base64 and split —
then discards it:

```java
String g40477 = "barbarians_at_the_gate"; // This is static so this whole flow is 'safe'
String bar = thing.doSomething(g40477);   // reflection
```

The sink is a genuine concatenation into an executed query:

```java
String sql = "SELECT * from USERS where USERNAME=? and PASSWORD='" + bar + "'";
PreparedStatement statement = connection.prepareStatement(sql);
```

Note it parameterises `USERNAME` but concatenates `PASSWORD`. In production
code that is a real vulnerability; here it is safe only because `bar` traces to
a literal through an unresolvable reflective call.

**Contrast to state in the paper:** the same analyser records **0% false
positives on 30 real-world files**. Real sanitisation looks like a
PreparedStatement, an allowlist, or an encoder — all handled correctly.

## 5. Limitation wording (precise, quantified)

> Our taint analysis is intra-procedural and models neither reflective dispatch
> nor container element-sensitivity. Approximately 70% of OWASP false positives
> stem from reflective indirection, which is intractable without whole-program
> analysis; a further ~25% would require field-sensitive container modelling and
> constant propagation, which we identify as future work.

---

## 6. Future-work direction supported by the literature

SecureAssist's model currently **never rejects a static finding** — verified
across the full run. It operates as an additive detector, which is why the
hybrid gains recall and loses precision in equal measure.

arXiv:2601.22952 shows LLM post-filtering cutting FP rates from >92% to 6.3%.
Adjudicating findings rather than extending them is therefore an evidenced
direction, not speculation.
